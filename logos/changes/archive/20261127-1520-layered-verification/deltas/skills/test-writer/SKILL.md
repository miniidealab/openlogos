## ADDED — 主链路用例小节（layered-verification）

> 来源变更：layered-verification（功能规格 §2.109.3、§2.109.10；`spec/test-results.md`「分层验收（layered-verification）」）。

主链路用例是「坏了就等于产品不可用」的核心用户路径上的用例。分层验收开启的项目，每个提案的验收都会跑它们，所以必须**少、快、绝对稳定**。主链路是规格的一部分，写在测试用例文档里，随提案的 delta 评审。

**写法**：在测试用例文档中加一个二级或三级标题，标题文本为「主链路用例」（英文项目用 `Main Path Cases`），其下用列表列出本文档中属于主链路的用例 ID；ID 之后可以写一句说明：

```markdown
- UT-S01-01 — 用户能登录
- ST-S01-02
```

**不要在用例表首格加任何标记**：首格只允许裸 ID 与 `[manual]` / `[manual/<平台>]`。主链路只通过这个小节表达。

**入选判据**（三条都满足才列入）：

1. 它验证的行为失效，就等于产品的核心功能不可用——不是「某个选项不生效」，而是「用户无法完成主要任务」。
2. 执行快：不依赖长时间等待、大批量数据或外部服务。
3. 绝对稳定：结果不随负载、时序或机器变化。**曾经偶发失败的用例不得列入**——分层开启时，主链路用例首跑失败、复跑通过不按偶发放行，verify 直接判 FAIL。

**不得列入**：

- 人工用例（`[manual]`）与 SMOKE；
- 本文档用例表中没有定义的 ID（主链路小节只能列本文档的用例）；
- 同一 ID 重复；一个文档只能有一个主链路小节。

**规模**：全项目主链路用例总数有上限（`verify.layered.main_path_max`，缺省 50）。超过上限时 verify 判 FAIL。新增一条主链路用例之前，先看是否有一条可以移出。

**谁决定**：主链路由产品负责人（或 leader）与研发共同定义。AI 只提出建议——在提案中写明建议新增、移出或替换哪些用例及理由，由用户在批准方案时决定；不要在用户没有同意的情况下修改主链路小节。

**检查**：`openlogos change-lint` 对小节写错（`main_path_invalid`）与超过上限（`main_path_over_limit`）给出警告；分层开启的项目上，verify 会据此在执行测试之前判 FAIL。
