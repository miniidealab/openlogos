## MODIFIED — 2.51 merge 合规判定单点与门禁可满足性保障


### 2.51.1 功能目标与职责边界

本功能不新增门禁、不改变任何一道门的判据内容，只做三件事：让准入点采信完整结论、让判据的多种读法从单一权威派生、让「门在其阶段可满足」这件事有可执行的失败信号。

架构 §四十一.4 已冻结「一个判据只能有一个实现」。此前识别的三种分裂形态是「权威 helper 被绕过」「同一常量各列一份」「投影只有冻结没有锚」。本功能补上**第四种形态**：

> **消费方自建缩水副本**——权威判据存在、也确实被调用了，但消费方只采信它的一部分结论。

这一形态比前三种更隐蔽：调用链看上去是对的，`runChangeLint` 确实跑了，日志里也有它的结果；分裂藏在**结果被怎样使用**这一步。

### 2.51.2 merge 准入判据

`merge` 对提案合规性的判定**等于** `change-lint` 的完整结论：

| 维度 | 此前 | 此后 |
|---|---|---|
| 是否运行预检 | 仅当提案带 `baseline_closure` 声明或 `[MODIFY]`/`[CREATE]` 任务标记 | 无条件运行 |
| 采信哪些违规 | 只保留 `BASELINE_CLOSURE_VIOLATION_CODES` 共 9 个码 | 全部违规 |
| 阻断条件 | 过滤后非空 | `violations` 非空 |
| 与 `merge-apply` 路径的关系 | 判据不同 | 逐字同源 |

**可预测性契约**：用户在 merge 前运行 `openlogos change-lint`，即可完全预知 merge 的准入结果。不存在「lint 红而 merge 绿」或反向的情形。这是简化带来的直接收益——此前用户无法靠 lint 判断能否 merge，只能试。

### 2.51.3 门禁阶段可满足性的可执行保障

架构 §四十一.1 已冻结「门禁的前置条件必须在该门所处状态下可满足」。但该不变量至今只是架构文字，没有任何自动手段能发现它被违反——plan 门死锁能长期潜伏正源于此。

本功能把它变成可执行断言：**对每一道门，构造该门所处阶段的合法最小提案，断言其通过**。

「合法最小提案」的含义是：只包含该阶段按流程定义应当存在的产物，不多不少。例如 merge 阶段的最小提案含完整 proposal/tasks 与全部 delta、不含 `[code]` 切片；plan 阶段的最小提案不含任何 delta。

这条断言的价值不在于验证当前 11 道门（它们都已核对为可满足），而在于**新增门禁时立刻给出失败信号**。没有它，一道在自己阶段不可能过的门可以静默存在很久，直到有人被它卡死。

### 2.51.4 收紧不等于误伤

准入收紧会拒绝更多提案。「误伤」特指提案本身合规却过不了，它只有两个来源：

| 来源 | 判定方法 | 本次结论 |
|---|---|---|
| 门在其阶段不可满足 | 逐门核对该阶段应有的产物是否足以满足其前置 | 10 道门全部可满足；其中 L8 本就是为 merge 前这一刻设计的 |
| 门依赖作者控制不了的外部状态 | 逐门核对其读取范围是否超出提案目录 | 仅 L8 读当前主文档；单活跃提案模型下无并发提案能改动同一章节 |

因此收紧后被拒绝的提案，都是真的不合规。这一结论由 §2.51.3 的可执行断言持续保障，而非一次性人工核对。

### 2.51.5 诊断的可归因要求

阻断必须让用户知道**改哪个文件的哪一处**。两条硬要求：

1. **逐条输出**：每条违规单独打印 `code`、路径、具体字段与 `fix_hint`；禁止只给「L1-L9 未全过」这类聚合结论。
2. **点名具体对象**：诊断中必须出现导致失败的实体本身——测试 ID、文件路径、字段名、章节锚。禁止「为空、非法或不在某集合中」这类无法定位的措辞。

反面教材是历史上的两处：围栏多命中时静默返回空集，用户只看到一条指向错误位置的诊断，而无从知道真实原因是围栏被多算了一个；以及对测试 ID 的诊断只说「不在 effective test view」而不说是哪一个。

### 2.51.6 YAML 围栏提取的唯一判据

全部 YAML 围栏提取器共用 `markdown-scan` 的 fence-aware 掩码，不得自建裸正则——裸正则对含嵌套围栏的文档会比 fence-aware 多命中一个围栏。

**多命中不得静默降级**：任一提取器在候选数不为 1 时，必须产出点名的诊断，说明命中了几处、分别在哪；不得静默返回空集或取第一个命中。

### 2.51.7 测试 ID 语法的唯一权威与具名读法

语法与其读法从单一模块派生，对外提供三种**具名**读法：

| 读法 | 用途 | 与权威语法的关系 |
|---|---|---|
| 结构化判定 | `test-change-set` / `test-slice-manifest` 判断字符串是否为合法测试 ID | 完整语法 |
| 表格首列提取 | 从测试规格表格提取 ID | 完整语法 + 行首锚定 |
| 正文扫描 | `automation-diagnostic` 在散文中查找 ID 提及 | 完整语法减去 SMOKE（正文提及 SMOKE 不构成用例引用） |

**读法不同是正当的，各自定义不是。** 本次消除的是四份独立演化的定义，不是读法差异本身。

**语法放宽以接纳现存 ID**：已合并规格中 11 个 `UT-JSON-*` / `ST-JSON-*` 此前不被结构化读法接纳，对它们的改动绕过切片归属、也不进 verify 可选集。放宽后这些用例从「静默不可见」变为「被覆盖」。不改名——删除已合并规格中的表格首列 ID 正是条目守恒要拦的形态。

**语法与数据的一致性锚**：断言已合并测试规格中每一个表格首列 ID 都被权威语法接纳。这是本节唯一能防止同类缺陷复发的机制——原始缺陷不是正则写错了，而是**没人检查正则与真实数据是否还对得上**。

### 2.51.8 安装态候选 runner 的留痕普遍要求

依赖历史制品的安装态 runner，在制品缺失时必须写显式 skip 并携带缺失项。这是既有契约，本次把它从「个别 runner 遵守」提升为**对全部已注册候选 runner 的普遍要求**，并加元测试断言每个注册项都实现了它。

不加元测试的后果已经发生过：三个历史 runner 因缺该契约而硬失败，使**任何后续提案的 Gate 3.8 被永久拉黑**——与被测能力毫无关系。

### 2.51.9 兼容、失败与发布边界

- 既有提案的 `change-lint` 判定逐字不变；变化只在 `merge` 是否采信其完整结论。
- 语法放宽只增不减：不存在此前被接纳、此后被拒绝的 ID。
- package / plugin / asset identity 统一提升为本地 candidate `0.14.9`；全局 `0.14.8` 作为固定回滚制品。
- 不执行 npm publish、dist-tag、Git tag、GitHub Release、官网发布或 git push。
