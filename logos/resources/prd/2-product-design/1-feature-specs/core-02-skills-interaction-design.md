# AI Skills 交互设计

> Phase 2 产品设计 · AI Skills 场景交互规格
>
> 涵盖场景：S02、S03、S12、S04、S05、S06（test-writer + test-orchestrator）、S07
>
> 最后更新：2026-04-02

## 通用交互模式

所有 AI Skills 遵循统一的交互模式：

### 触发 → 检查 → 执行 → 输出

```
用户输入自然语言 → AI 识别意图 → 匹配 Skill
    → 检查前置条件（前序阶段文档是否存在）
        → 条件不满足 → 提示缺失项，建议先完成前序阶段
        → 条件满足 → 检查信息充分度
            → 信息不足 → 追问（最多 3 轮）
            → 信息充分 → 执行 Skill，生成产出物
    → 输出文档到指定目录
    → 询问用户是否需要调整
```

### 追问策略

- **最多 3 轮追问**，每轮聚焦 1 个关键信息缺口
- 第 1 轮：产品/场景的核心定义（"你要做什么"）
- 第 2 轮：关键约束（"有什么限制"）
- 第 3 轮：优先级确认（"先做哪些"）
- 如果 3 轮后信息仍不足，基于已有信息先输出初稿，标注需要确认的假设

### 产出物命名规范

所有 Skill 产出的文件遵循统一命名：`{序号}-{描述}.md`，场景编号在文档内容中而非文件名中体现。

## S02: AI 辅助写需求文档 — 交互规格

**对应 Skill**：`prd-writer`

**前置条件**：项目已初始化（S01 完成）

**对话流程**：

| 步骤 | 角色 | 内容 |
|------|------|------|
| 1 | 用户 | 「帮我写需求文档」（可附带产品描述） |
| 2 | AI | 检查 `logos/resources/prd/1-product-requirements/` 是否已有文件 |
| 2a | AI | 已有文件 → 「已存在需求文档，是要修改还是重写？」 |
| 2b | AI | 无文件 → 进入 Step 3 |
| 3 | AI | 评估用户提供的信息量 |
| 3a | AI | 信息充分（含定位 + 用户 + 痛点）→ 直接进入 Step 6 |
| 3b | AI | 信息不足 → 追问 Step 4 |
| 4 | AI | 「请先告诉我：这个产品要解决什么人的什么问题？」 |
| 5 | 用户 | 描述产品定位和目标用户 |
| 6 | AI | 基于所有信息，按 prd-writer 规范输出完整需求文档 |
| 7 | AI | 「需求文档初稿已生成到 `logos/resources/prd/1-product-requirements/01-requirements.md`，请 review 后告诉我需要修改的地方」 |

**AI 行为规范**：
- 输出的文档**必须**包含：产品背景、痛点分析、场景总览表、核心场景验收条件（GIVEN/WHEN/THEN）、约束与边界
- 场景编号从 S01 开始自动分配
- 每个 P0/P1 场景至少 1 个正常 + 1 个异常验收条件
- 不生成空壳文档——如果关键信息缺失，宁可追问也不占位

### 验收条件（交互级）

#### 正常：用户信息充分
- **GIVEN** 项目已初始化，用户在第一条消息中描述了产品定位、目标用户和核心痛点
- **WHEN** AI 开始执行 prd-writer Skill
- **THEN** AI 不追问，直接输出完整需求文档到指定目录

#### 正常：用户信息不足
- **GIVEN** 项目已初始化，用户只说了「帮我写需求文档」
- **WHEN** AI 开始执行 prd-writer Skill
- **THEN** AI 追问产品定位 → 用户回答 → AI 输出需求文档（追问不超过 3 轮）

#### 异常：已有需求文档
- **GIVEN** `logos/resources/prd/1-product-requirements/01-requirements.md` 已存在
- **WHEN** 用户说「帮我写需求文档」
- **THEN** AI 询问「已存在需求文档，是要在此基础上修改，还是全部重写？」

## S03: AI 辅助做产品设计 — 交互规格

**对应 Skill**：`product-designer`

**前置条件**：Phase 1 需求文档存在

**对话流程**：

| 步骤 | 角色 | 内容 |
|------|------|------|
| 1 | 用户 | 「基于需求文档做产品设计」 |
| 2 | AI | 检查 `logos/resources/prd/1-product-requirements/` 是否有文件 |
| 2a | AI | 无文件 → 「未找到需求文档，请先完成 Phase 1」 |
| 2b | AI | 有文件 → 读取需求文档，提取场景清单 |
| 3 | AI | 判断产品类型（Web / CLI / AI Skill / 混合） |
| 4 | AI | 「我从需求文档中识别到 N 个场景，产品类型为 [类型]。将按场景逐个设计交互规格和原型。先从 S01 开始？」 |
| 5 | 用户 | 确认或调整顺序 |
| 6 | AI | 逐场景输出交互规格 + 原型 |
| 7 | AI | 「S01 的产品设计已完成，继续 S02？」 |

**AI 行为规范**：
- 先判断产品类型，选择对应的原型形式
- 按场景组织文档，不按页面组织
- 场景编号与 Phase 1 严格一致
- 如果场景需要拆分为子场景，先说明理由再拆

### 验收条件（交互级）

#### 正常：完整的产品设计
- **GIVEN** Phase 1 需求文档存在且包含场景清单
- **WHEN** 用户要求做产品设计
- **THEN** AI 判断产品类型，按场景逐个输出交互规格和原型，存放在 `logos/resources/prd/2-product-design/`

#### 异常：缺少需求文档
- **GIVEN** `logos/resources/prd/1-product-requirements/` 为空
- **WHEN** 用户要求做产品设计
- **THEN** AI 提示「未找到需求文档，请先完成 Phase 1」

## S12: AI 辅助技术架构设计 — 交互规格

**对应 Skill**：`architecture-designer`

**前置条件**：Phase 2 产品设计文档存在

**对话流程**：

| 步骤 | 角色 | 内容 |
|------|------|------|
| 1 | 用户 | 「帮我设计技术架构」 |
| 2 | AI | 检查 Phase 2 文档是否存在 |
| 2a | AI | 不存在 → 「未找到产品设计文档，请先完成 Phase 2」 |
| 2b | AI | 存在 → 读取需求文档 + 产品设计文档 |
| 3 | AI | 「根据你的产品特征，我建议以下架构方案。有没有技术偏好或约束？比如已经确定了某个框架或云服务商？」 |
| 4 | 用户 | 提供技术偏好（如"用 Next.js + Supabase"）或说"你推荐" |
| 5 | AI | 输出架构概要文档（架构图 + 选型表 + 部署拓扑） |
| 5a | AI | 识别架构中的外部服务依赖（邮件、短信、验证码、支付、OAuth 等） |
| 5b | AI | 如果识别到外部依赖 → 「我发现项目依赖以下外部服务：[列表]。为了后续编排测试能顺利执行，需要为每个依赖确定测试策略。」 |
| 5c | AI | 逐个询问「[依赖名] 推荐使用 [策略] 策略（[说明]），你同意吗？或者有其他偏好？可选：test-api / fixed-value / env-disable / mock-callback / mock-service」 |
| 5d | 用户 | 确认或调整每个依赖的测试策略 |
| 6 | AI | 将技术栈写入 `logos-project.yaml` 的 `tech_stack`，将外部依赖和测试策略写入 `external_dependencies` |
| 7 | AI | 「架构概要已生成。我已将技术栈和外部依赖测试策略写入 `logos-project.yaml`，请确认是否需要调整」 |

**AI 行为规范**：
- 根据产品复杂度调整架构文档的详细程度
- 选型表每项必须有选型理由
- 必须更新 `logos-project.yaml` 的 `tech_stack`
- 如有外部依赖，必须更新 `logos-project.yaml` 的 `external_dependencies`
- 不预设技术栈——如果用户没有偏好，给出 2-3 个方案对比让用户选择
- 主动为每个外部依赖推荐合适的测试策略，但最终由用户确认

### 验收条件（交互级）

#### 正常：有技术偏好
- **GIVEN** Phase 2 文档存在，用户明确了技术偏好
- **WHEN** 用户说「帮我设计技术架构，用 Next.js + Supabase」
- **THEN** AI 基于指定技术栈输出架构概要，更新 `logos-project.yaml`

#### 正常：无技术偏好
- **GIVEN** Phase 2 文档存在，用户未指定技术
- **WHEN** 用户说「帮我设计技术架构」
- **THEN** AI 追问技术偏好，或给出 2-3 个方案对比供选择

#### 正常：包含外部服务依赖
- **GIVEN** Phase 2 文档存在，架构中涉及邮件/短信/支付等外部服务
- **WHEN** AI 完成架构概要后识别到外部依赖
- **THEN** AI 主动列出外部依赖清单，逐个推荐测试策略并与用户确认，最终写入 `logos-project.yaml` 的 `external_dependencies` 字段

#### 正常：无外部依赖
- **GIVEN** 项目为纯 CLI 工具或无外部服务依赖
- **WHEN** AI 完成架构概要
- **THEN** AI 跳过外部依赖测试策略步骤，不生成 `external_dependencies` 字段

## S04: AI 辅助场景建模 — 交互规格

**对应 Skill**：`scenario-architect`

**前置条件**：Phase 1/2 文档 + 技术架构概要（S12）存在

**对话流程**：

| 步骤 | 角色 | 内容 |
|------|------|------|
| 1 | 用户 | 「帮我画 S01 的时序图」或「帮我做场景建模」 |
| 2 | AI | 检查前置文档（需求 + 产品设计 + 架构概要） |
| 2a | AI | 缺失 → 提示具体缺什么，建议先完成 |
| 2b | AI | 齐全 → 读取 S01 的全部上下文 |
| 3 | AI | 输出 Mermaid 时序图 + 步骤说明 + 异常用例 |
| 4 | AI | 「S01 的时序图已完成，包含 N 个 Step 和 M 个异常用例。需要调整吗？」 |
| 5 | 用户 | 确认或要求调整 |
| 6 | AI | 「继续画 S02？」 |

**AI 行为规范**：
- 时序图的参与方必须与架构图中的系统组件一致
- 场景编号沿用 Phase 1
- 每个涉及外部调用的 Step 至少 1 个异常用例

### 验收条件（交互级）

#### 正常：指定场景
- **GIVEN** 前置文档齐全
- **WHEN** 用户说「帮我画 S01 的时序图」
- **THEN** AI 输出 S01 的 Mermaid 时序图、步骤说明、异常用例，存放在指定目录

#### 正常：批量建模
- **GIVEN** 前置文档齐全
- **WHEN** 用户说「帮我做所有 P0 场景的建模」
- **THEN** AI 逐场景输出，每完成一个询问是否继续

#### 异常：场景编号不存在
- **GIVEN** 需求文档只定义了 S01-S05
- **WHEN** 用户说「帮我画 S06 的时序图」
- **THEN** AI 提示「S06 在需求文档中未定义，是否需要先在 Phase 1 补充？」

## S05: AI 辅助设计 API 和 DB — 交互规格

**对应 Skill**：`api-designer` + `db-designer`

**前置条件**：时序图已完成

**对话流程**：

| 步骤 | 角色 | 内容 |
|------|------|------|
| 1 | 用户 | 「帮我设计 API」 |
| 2 | AI | 检查时序图是否存在 |
| 2a | AI | 不存在 → 「未找到时序图，请先完成 Phase 3 Step 1」 |
| 2b | AI | 存在 → 从时序图中提取所有跨系统调用 |
| 3 | AI | 「从时序图中识别到 N 个 API 端点，按领域分组后有 M 个文件。开始生成 OpenAPI YAML？」 |
| 4 | 用户 | 确认 |
| 5 | AI | 输出 OpenAPI YAML（按领域分文件） |
| 6 | AI | 「API 设计完成。是否继续推导数据库 DDL？」 |
| 7 | 用户 | 确认 |
| 8 | AI | 读取 `logos-project.yaml` 确认数据库类型，输出对应方言的 DDL |
| 9 | AI | 「API + DB 设计已完成，请 review」 |

**AI 行为规范**：
- API 端点必须可追溯到时序图 Step 编号
- DB 方言由 `logos-project.yaml` 的 `tech_stack.database` 决定
- API 和 DB 分步输出，给用户 review 机会

### 验收条件（交互级）

#### 正常：API + DB 连续设计
- **GIVEN** 时序图已完成
- **WHEN** 用户说「帮我设计 API」
- **THEN** AI 先输出 OpenAPI YAML，询问是否继续 → 输出 DB DDL

#### 异常：无时序图
- **GIVEN** 时序图目录为空
- **WHEN** 用户要求设计 API
- **THEN** AI 提示先完成场景建模

## S06: AI 辅助设计测试用例 — 交互规格

S06 分为两个子步骤，由两个 Skill 协作完成：

### Step 3a: 单元测试 + 场景测试用例设计

**对应 Skill**：`test-writer`

**前置条件**：时序图 + API YAML + DB DDL 已完成（或非 API 项目时仅需时序图）

**跳过条件**：不可跳过，所有项目类型都必须执行

**对话流程**：

| 步骤 | 角色 | 内容 |
|------|------|------|
| 1 | 用户 | 「帮我设计测试用例」或「帮我设计 S01 的测试」 |
| 2 | AI | 检查前置文档（时序图必须存在；API YAML、DB DDL 可选） |
| 2a | AI | 时序图不存在 → 「未找到时序图，请先完成 Phase 3 Step 1」 |
| 2b | AI | 时序图存在 → 读取时序图 + API YAML + DB DDL（如果有） |
| 3 | AI | 「从 S01 的时序图中识别到 N 个 Step、M 个 EX 异常用例。将从 API 字段约束和 DB 约束中提取单元测试用例，从 Step 序列中提取场景测试用例。开始设计？」 |
| 4 | 用户 | 确认 |
| 5 | AI | 输出测试用例规格文档（Markdown），包含单元测试用例和场景测试用例 |
| 6 | AI | 「S01 的测试用例已设计完成：X 个单元测试用例 + Y 个场景测试用例，存放在 `logos/resources/test/S01-test-cases.md`」 |
| 7 | AI | 判断项目类型：涉及 API → 「继续进入 Step 3b 设计 API 编排测试？」；不涉及 API → 「测试设计已完成，建议进入代码生成阶段」 |

**AI 行为规范**：
- 单元测试用例来源：API 字段约束（类型、格式、长度）、DB 约束（UNIQUE、CHECK、NOT NULL）、业务规则、EX 中的单点错误处理
- 场景测试用例来源：时序图 Step 序列（主路径）、EX 异常用例（异常路径）、Phase 1/2 验收条件
- 每个用例必须包含：用例 ID、描述、前置条件、输入、预期输出
- 场景测试用例必须标注覆盖的 Step 范围和 EX 编号

### Step 3b: API 编排测试设计

**对应 Skill**：`test-orchestrator`

**前置条件**：Step 3a 已完成 + API YAML 已完成

**跳过条件**：项目不涉及 API（纯 CLI / 静态站点等）

**对话流程**：

| 步骤 | 角色 | 内容 |
|------|------|------|
| 1 | 用户 | 确认继续（承接 Step 3a 的引导）或主动说「帮我设计编排测试」 |
| 2 | AI | 检查 `logos/resources/api/` 是否有文件 |
| 2a | AI | 无文件 + 架构包含 API → 「未找到 API 规格，请先完成 Phase 3 Step 2」 |
| 2b | AI | 无文件 + 架构不含 API → 「当前项目不涉及 API，编排测试可跳过，建议直接进入代码生成」 |
| 2c | AI | 有文件 → 读取 API YAML + 时序图 |
| 2d | AI | 读取 `logos-project.yaml` 的 `external_dependencies` 字段 |
| 2e | AI | 如果时序图中有外部服务调用但 `external_dependencies` 中未声明 → 提醒用户补充 |
| 2f | AI | 如果 `external_dependencies` 中某依赖缺少 `test_strategy` → 主动追问 |
| 3 | AI | 「从 API 规格中识别到 N 个场景的调用链，其中 K 个步骤涉及外部依赖（已匹配 mock 策略）。开始生成编排测试？」 |
| 4 | 用户 | 确认 |
| 5 | AI | 逐场景输出编排测试 JSON（正常路径 + 异常路径），涉及外部依赖的步骤自动插入 `mock` 字段 |
| 6 | AI | 「编排测试已完成，覆盖 N 个正常流程 + M 个异常流程，其中 K 个步骤使用了 mock 策略。测试设计全部完成，建议进入代码生成阶段」 |

### 验收条件（交互级）

#### 正常：生成单元测试 + 场景测试用例（Step 3a）
- **GIVEN** 时序图、API YAML 和 DB DDL 已完成
- **WHEN** 用户说「帮我设计测试用例」
- **THEN** AI 为场景生成单元测试用例和场景测试用例，输出 Markdown 文档到 `logos/resources/test/`

#### 正常：非 API 项目的测试设计（仅 Step 3a）
- **GIVEN** 项目为纯 CLI 工具，时序图已完成
- **WHEN** 用户说「帮我设计测试用例」
- **THEN** AI 执行 Step 3a 生成测试用例规格，提示 Step 3b 可跳过

#### 正常：生成编排测试（Step 3b）
- **GIVEN** Step 3a 已完成，API YAML 和时序图已完成
- **WHEN** 用户继续进入 Step 3b
- **THEN** AI 为每个场景生成正常 + 异常编排测试 JSON

#### 正常：场景包含外部依赖
- **GIVEN** API YAML 和时序图已完成，`logos-project.yaml` 中声明了 `external_dependencies`
- **WHEN** AI 执行 Step 3b
- **THEN** AI 读取 `external_dependencies`，在涉及外部服务的步骤中自动插入 `mock` 字段，输出摘要中包含 mock 步骤统计

#### 异常：缺少时序图
- **GIVEN** 时序图目录为空
- **WHEN** 用户要求设计测试用例
- **THEN** AI 提示先完成场景建模

## S07: AI 辅助生成代码 + 测试代码 — 交互规格

**对应能力**：AI 编程工具原生能力（不是独立 Skill，而是利用完整上下文）

**前置条件**：测试设计完成（S06），所有前序阶段已完成

**对话流程**：

| 步骤 | 角色 | 内容 |
|------|------|------|
| 1 | 用户 | 「按 S01 的规格帮我实现」 |
| 2 | AI | 检查 S01 的全部上下文文档是否齐全（含测试用例规格） |
| 2a | AI | 缺失 → 列出缺失文件清单（含 `logos/resources/test/S01-test-cases.md`），建议先补全 |
| 2b | AI | 齐全 → 读取 S01 的需求 + 设计 + 时序图 + API + DB + 测试用例规格 + 编排测试 |
| 3 | AI | 「S01 的上下文已加载，包含 N 个 Step、M 个 API 端点、K 个异常用例、X 个单元测试用例、Y 个场景测试用例。开始生成代码？」 |
| 4 | 用户 | 确认 |
| 5 | AI | 按时序图 Step 逐步生成业务代码 + 单元测试代码 + 场景测试代码 |
| 6 | AI | 「S01 代码生成完成（含业务代码 + 测试代码），请 review。要继续 S02 吗？」 |

**AI 行为规范**：
