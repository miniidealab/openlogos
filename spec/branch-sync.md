# 提案分支同步主分支规范

> 版本: 1.0.0 | 来源变更：branch-sync-generated-files（决策 C01；proposal-r1 F1～F4 处置）
> 场景：S44。JSON 形态见 `spec/cli-json-output.md`「`openlogos branch sync|status --format json`」；配置项的契约见 §4.3 与 §4.8。

## 1. 范围

本规范定义 `openlogos branch sync` 与 `openlogos branch status` 的规范性行为：把主分支同步进当前分支时，哪些文件由 CLI 直接处置、登记表如何合并、什么情况下拒绝执行、结果如何表达。

不在范围内：规格文档与代码冲突的处理、统一发号、创建分支与工作目录、创建合并请求、推送与拉取。

术语：

- **主分支**：本次要同步进来的那条分支，按 §3 确定。
- **本分支**：执行命令时工作目录所在的分支（HEAD）。
- **共同起点**：本分支与主分支的合并基点（`git merge-base`）。
- **同步处置清单**：同步时一律取主分支版本的文件集合，按 §4 确定。
- **登记表**：`logos/logos-project.yaml`。

## 2. 命令

```bash
openlogos branch sync   [--base <ref>] [--format json]
openlogos branch status [--base <ref>] [--format json]
```

- 两个命令都必须在项目根（`logos/logos.config.json` 所在目录）运行，不要求存在活跃提案。
- 两个命令都只调用本机的 git，不联网、不读写凭据。`branch sync` 不推送、不拉取、不创建分支；主分支的引用是否最新由调用方负责。
- `branch status` 只读：不修改任何文件、不取锁、不过恢复门。

## 3. 主分支的确定

按顺序取第一个给出的来源：

| 顺序 | 来源 | `source` 取值 | 引用 |
|---|---|---|---|
| 1 | `--base <ref>` | `flag` | 参数原文 |
| 2 | `logos/logos.config.json` 的 `branch_sync.base_branch` | `config` | 配置原文 |
| 3 | 远端 `origin` 的默认分支（`refs/remotes/origin/HEAD` 指向的远端跟踪分支） | `remote-default` | 如 `origin/main` |

- 取到的引用必须能解析为一个提交（`<ref>^{commit}`）。排在前面的来源一旦给出就不再回落：它解析不到提交时直接报错，不改用后面的来源。
- 三个来源都没有，或取到的引用解析不到提交：`BRANCH_BASE_UNRESOLVED`，提示用 `--base` 显式指定。
- 本分支与主分支没有共同起点：`BRANCH_NO_MERGE_BASE`。

## 4. 同步处置清单

### 4.1 准入标准

清单只收**重新验收就会整份重写**的文件。判断一个文件能否进清单，只问一个问题：同步之后重新执行 `openlogos verify`（及项目自己的验收步骤），这个文件会不会被整份写出来。会，才可以进清单。

记录已经发生的事实的文件（哪次部署、哪次基线事务）与承载事务恢复的材料不满足这一标准，不得进清单。

### 4.2 内置项

内置项的路径只读地复用 verify 既有的路径解析结果，不另行定义。verify 对结果路径的取值几乎不设限制，所以内置项与追加项一样要经过 §4.5 的保护路径校验：

| 内置项 | 路径来源 |
|---|---|
| 共用验收报告 | `logos/resources/verify/acceptance-report.md` |
| 模块验收报告 | 登记表登记了两个及以上模块时，每个已登记模块 `<m>` 的 `logos/resources/verify/<m>-acceptance-report.md` |
| 测试结果账本 | 规范化后的 `verify.result_path`（缺省 `logos/resources/verify/test-results.jsonl`） |
| 回归、增量结果 | 配置了 `verify.regression_result_path` / `verify.incremental_result_path` 时的对应路径 |

### 4.3 项目追加项

项目可在 `logos/logos.config.json` 的 `branch_sync.replace_paths` 中追加路径。条目语法：

- 项目根相对路径，`/` 分隔；以 `/` 结尾表示该目录下的全部文件，否则只表示单个文件；
- `*` 只能独占一个路径段，恰好匹配一个段；
- 拒绝：绝对路径、含 `..` / `.` / 空段、含反斜杠、空串。

约束：条目必须位于 `logos/resources/verify/` 之下。任一条目不满足语法或该约束：`BRANCH_SYNC_CONFIG_INVALID`，`branch sync` 拒绝执行，不做任何改动。`branch_sync` 不是对象、`replace_paths` 不是字符串数组、`base_branch` 不是非空字符串同样按此处理。

条目与保护路径的重叠由 §4.5 对整份清单统一校验。

### 4.4 不进清单的文件

以下文件按普通文件交给 git 合并，CLI 不替换也不删除：

| 文件 | 原因 | 是否保护路径 |
|---|---|---|
| 基线运行目录 `logos/resources/verify/baseline-seed-runs/`（每次运行的 `staging/`、`resolved/`、`backup/`、`commit-journal.json`、`run.json`，以及模块锁文件） | 一次基线事务的输入与崩溃恢复材料 | 是 |
| 基线事件账本 `logos/resources/verify/baseline-events.jsonl` | 逐条追加的事件记录 | 是 |
| 部署报告 `logos/resources/verify/deployment-report.md` 与 `logos/resources/verify/<m>-deployment-report.md` | 逐次追加的部署记录 | 是 |
| 部署制品与证据包（`logos/resources/verify/` 下的其他子目录） | 某次部署或验收留下的证据 | 否 |
| 冒烟结果与报告 | 取决于已部署的环境，不能只凭同步后的代码重新得出 | 否 |

「保护路径」不能经任何来源进入清单，见 §4.5。

基线运行目录另有一条保守规则：对其中任一被跟踪的文件，两条分支相对共同起点都做了改动且结果不同（含一边修改一边删除）时，无论 git 是否自动合并成功，CLI 都把它报告为剩余冲突（§8）。两条分支各自独有的运行位于不同目录，互不影响，同步后都保留。

### 4.5 整份清单的保护路径校验

内置项与追加项合成清单之后，对清单中的**每一个**路径统一校验：不得与 §4.4 的保护路径重叠（等于、覆盖或落在其内部都算重叠）。校验不区分路径来自哪个配置项。

- 命中时以 `BRANCH_SYNC_CONFIG_INVALID` 拒绝执行，不做任何改动，并点名来源配置项：`verify.result_path`、`verify.regression_result_path`、`verify.incremental_result_path` 或 `branch_sync.replace_paths`。
- 例：`verify.result_path` 指向 `logos/resources/verify/deployment-report.md` 或 `logos/resources/verify/baseline-seed-runs/r1/run.json` 时，`openlogos verify` 照旧接受该配置，但 `branch sync` 拒绝执行——同步不能因为 verify 允许某个结果路径，就把那里的部署记录或基线材料替换成主分支的版本或删除。
- 本校验只属于同步：不改变 verify 对这些配置的处理，也不限制结果路径落在验收目录之外的合法配置。

### 4.6 清单的用途

清单只供 `branch sync` 使用。verify 沙箱的写入白名单不读取清单，也不因 `branch_sync.replace_paths` 发生变化：「同步时可以整份替换」与「测试进程可以写入」是两种不同的许可。

清单在发起合并之前按本分支的配置与登记表计算一次，本次同步内不再重算。

### 4.7 处置规则

对清单命中的每个路径，只处理在本分支提交或主分支提交中被 git 跟踪的文件；未被跟踪或被 git 忽略的同名文件不动。「不动」由 §7.4 的占用检查保证：主分支要带进来的路径在工作区已被未入库的文件占用时，同步在发起合并之前就拒绝。

| 主分支提交中 | 本分支提交中 | 处置 | `action` |
|---|---|---|---|
| 有 | 有或无 | 工作区与索引取主分支的内容 | `took-base` |
| 无 | 有 | 从工作区与索引删除 | `deleted` |

处置与 git 是否对该路径报告冲突无关：清单内的路径一律按上表处理。两边内容本就相同的路径不计入结果。

### 4.8 配置项契约

`logos/logos.config.json` 新增可选对象 `branch_sync`，只被本规范的两个命令读取：

| 字段 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `branch_sync.base_branch` | 非空字符串 | 无 | 主分支的引用，见 §3 |
| `branch_sync.replace_paths` | 字符串数组，元素不重复 | `[]` | 项目追加的同步处置路径，见 §4.3、§4.5 |

`branch_sync` 不接受其他字段。`spec/logos.config.schema.json` 须包含与本表一致的 `branch_sync` 定义；该 JSON 文件的更新随本能力的实现一并交付（现有的章节合成不能对 JSON 文件做结构化插入），以本节为准。

## 5. 登记表合并

### 5.1 何时进行

读取登记表在三个提交中的版本：共同起点（O）、本分支（A）、主分支（B）。

- 三个版本都存在、都能解析为 YAML 映射，且 A、B 相对 O 都有改动：按 §5.2～§5.5 做条目合并，其结果取代 git 对该文件的文本合并结果。之所以不看 git 是否报告冲突，是因为两边各自推进计数器时 git 可能不报冲突而得到错误的值。
- 只有一边有改动，或两边都没有改动：不做条目合并，沿用 git 的结果（状态 `not-needed`）。
- 任一版本不存在、不能解析，或 §5.2 的键控列表形态不符合预期（不是数组、条目缺键、同一版本内键重复）：不做条目合并（状态 `skipped`，给出原因），沿用 git 的结果；git 对该文件报告了冲突时，它列入剩余冲突。

比较一律按解析后的值进行：映射的键顺序不影响相等，数组的元素顺序影响相等；不比较文本、注释与排版。

### 5.2 键控列表

| 顶层字段 | 键 |
|---|---|
| `modules` | `id` |
| `features` | `id` |
| `scenarios` | `id` |
| `resource_index` | `path` |

对每个键 k，按三个版本中该条目的情况决定结果：

| O | A | B | 结果 |
|---|---|---|---|
| 无 | 有 | 无 | 取 A（本分支新增） |
| 无 | 无 | 有 | 取 B（主分支新增） |
| 无 | 有 | 有，与 A 相同 | 取其一 |
| 无 | 有 | 有，与 A 不同 | **冲突** `both-added-different` |
| 有 | 与 O 相同 | 与 O 相同 | 保留 |
| 有 | 已修改 | 与 O 相同 | 取 A |
| 有 | 与 O 相同 | 已修改 | 取 B |
| 有 | 已修改 | 已修改，与 A 相同 | 取其一 |
| 有 | 已修改 | 已修改，与 A 不同 | **冲突** `both-modified` |
| 有 | 已删除 | 与 O 相同 | 删除 |
| 有 | 与 O 相同 | 已删除 | 删除 |
| 有 | 已删除 | 已删除 | 删除 |
| 有 | 已删除 | 已修改 | **冲突** `delete-modify` |
| 有 | 已修改 | 已删除 | **冲突** `delete-modify` |

某个键控列表在三个版本中都不存在时跳过；只在部分版本中存在时，不存在的一侧按空列表处理。

资源索引中人工写的描述是条目内容的一部分：只有一边改过描述时取改过的一边，两边都没改时原样保留，CLI 不重新生成任何已有条目的描述。

### 5.3 计数器

`scenario_counter.next_id`、`feature_counter.next_id`、`decision_counter.next_id` 为整数时，合并值取 A 与 B 中较大者（只有一边存在时取该边）。A 与 B 都大于 O 时，结果中给出 `both_advanced: true` 并附诊断 `counter_both_advanced`：两条分支各自取过号，可能存在重号。CLI 不检测、不修正重号（两边新增了相同编号而内容不同的条目，会由 §5.2 的 `both-added-different` 报出）。

计数器不是整数时按 §5.4 处理。

### 5.4 其余顶层字段

§5.2、§5.3 之外的每个顶层字段（`project`、`tech_stack`、`conventions`、`deployment_gates`、`baseline_index` 及任何未列出的字段）按整个值做三方比较：只有一边改动（含新增、删除）时取改动的一边；两边改动相同取其一；两边改动不同为**冲突** `both-modified`，键为字段名。

### 5.5 写回

- **全有或全无**：只要出现任何冲突，CLI 不写回登记表（状态 `conflict`），文件保持 git 合并后的内容，并列入剩余冲突（§8）；冲突逐条给出所在字段、键与类型。
- 没有冲突时（状态 `merged`）：以本分支版本的文档为底稿做结构化修改并写回，保留其注释与排版；被修改的条目在原位置替换，被删除的条目移除，主分支新增的条目按其在主分支中的相对顺序追加在所属列表末尾。写回前必须确认结果仍可解析，否则不写盘并按 §7.2 失败处理。
- 写回之后调用既有的资源索引补录（`openlogos sync` 所用的同一实现）：只为磁盘上存在、索引中没有且命中推断规则的文件追加条目，不修改、不删除已有条目。补录条数计入结果。
- 写回与补录完成后把登记表加入索引。

## 6. 与基线事务的关系

`branch sync` 会改写登记表，基线事务（`openlogos baseline-seed`）也写这个文件，二者共用既有的模块级事务锁与恢复门，不另设互斥机制。

顺序是**先取锁、后检查**，与 `baseline-seed` 自身的做法一致。检查若排在取锁之前，基线进程可以在两者之间取得锁、写下未终结的提交记录并释放锁，同步随后拿到锁时那次检查已经过期。

1. 发起合并之前，按模块 id 升序取得本分支登记表中每个模块的事务锁（没有模块登记或登记表读不出时按单个模块 `core`）。任一把锁拿不到：释放已取得的锁，以 `baseline_commit_in_progress` 拒绝。
2. 持有全部锁之后，对每个模块检查未终结的基线提交记录：存在未终结的记录、记录损坏或无法判定时，释放全部锁，以 `baseline_commit_in_progress` 拒绝，提示先完成恢复。`branch sync` 自己不执行恢复。
3. 仍在持锁期间，重新确认取锁之前做过的仓库检查没有过期：HEAD 仍是开始时的那个提交；没有进行中的合并、变基等操作；已被跟踪的文件没有未提交改动；主分支引用解析出的提交未变。任一不成立：释放全部锁并拒绝——后三项沿用各自的前置条件错误码；HEAD 或主分支提交在此期间变了，说明另有进程在操作这个仓库，报 `BRANCH_OPERATION_IN_PROGRESS`。
4. 锁从取得起持有到命令结束（成功、仍有冲突或失败），结束时全部释放。
5. 以上拒绝都发生在发起合并之前，因此不做任何改动、不清除任何标记。

## 7. 执行顺序与失败处理

### 7.1 顺序

1. 检查前置条件（§7.3）。
2. 确定主分支与共同起点（§3）。本分支已包含主分支的提交：结果 `up-to-date`，直接结束——不产生提交、不清除标记、不取锁。
3. 计算同步处置清单并校验配置（§4）。
4. 取得模块锁，持锁检查基线提交记录并重新确认仓库检查（§6）。
5. 读取登记表的三个版本（§5.1）。
6. 发起合并：
   - 先做未入库文件的占用检查（§7.4）；命中即 `BRANCH_UNTRACKED_COLLISION`，不发起合并。
   - 选择合并方式（§7.5）：纯快进时快进到主分支，跳到第 9 步；否则执行一次不自动提交、不快进的合并。
   - git 拒绝发起合并：`BRANCH_SYNC_MERGE_FAILED`，此时仓库状态未变。
7. 按 §4.7 处置清单内的文件。
8. 按 §5 合并登记表。
9. 清除验收与交付标记（§9）。
10. 检查剩余冲突（§8）：没有则完成合并提交，结果 `synced`；有则保留合并现场，结果 `conflicts`。
11. 释放锁并输出结果。

### 7.2 中途失败

第 6 步合并已经发起之后，第 7～10 步中任何一步失败（读写错误、git 命令失败、登记表写回前自检不通过、提交失败）：

- 中止本次合并，使工作区、索引与分支指向回到同步前（纯快进路径上以回到同步前的提交恢复；该路径上不会有被覆盖的未入库文件，见 §7.4）；
- 以 `BRANCH_SYNC_FAILED` 报告，`details.restored` 说明是否已恢复，`details.step` 指出失败的步骤；恢复本身失败时 `restored: false`，并给出 `git merge --abort` 的提示；
- 已经清除的、未被 git 跟踪的标记不会随中止恢复。这只会让项目多验收一次，不会让过期的结论继续有效。

### 7.3 前置条件

以下任一条件不满足时拒绝执行，不做任何改动：

| 条件 | 错误码 |
|---|---|
| 当前目录是已初始化的 OpenLogos 项目根 | `PROJECT_NOT_INITIALIZED` |
| 当前目录在 git 仓库内且 git 可用 | `BRANCH_NOT_GIT_REPO` |
| 没有进行中的合并、变基、拣选、回退或二分查找 | `BRANCH_OPERATION_IN_PROGRESS` |
| 已被跟踪的文件没有未提交的改动（未跟踪的文件不算） | `BRANCH_WORKTREE_DIRTY` |
| 主分支可确定且有共同起点 | `BRANCH_BASE_UNRESOLVED` / `BRANCH_NO_MERGE_BASE` |
| `branch_sync` 配置合法 | `BRANCH_SYNC_CONFIG_INVALID` |
| 整份同步处置清单不与保护路径重叠（§4.5） | `BRANCH_SYNC_CONFIG_INVALID` |
| 能取得模块锁，且持锁检查时没有未终结的基线事务 | `baseline_commit_in_progress` |
| 主分支要带进来的路径在工作区没有被未入库的文件占用（§7.4） | `BRANCH_UNTRACKED_COLLISION` |

HEAD 处于分离状态不构成拒绝理由，结果中的分支名为 `null`。

### 7.4 未入库文件的占用检查

git 在真正的合并（非快进）中会直接覆盖被忽略的本地文件，`--no-overwrite-ignore` 只在快进时生效（实测 git 2.48.1：带该选项的 `git merge --no-ff --no-commit` 仍覆盖了被忽略的同名文件，`git merge --abort` 之后该文件消失）。未入库的内容一旦被覆盖，中止合并也找不回来。因此这项保护不能交给 git 的选项，由 CLI 在发起合并之前自行检查：

- 取「主分支提交中存在、本分支提交中不存在」的全部路径；
- 其中任一路径在工作区里已经有东西（文件、目录或链接，无论是未跟踪还是被忽略），或者它的某一级上级目录的位置上是一个文件：视为被占用；
- 有被占用的路径：以 `BRANCH_UNTRACKED_COLLISION` 拒绝并列出这些路径，不发起合并，不做任何改动。

检查对快进与不快进两种方式都执行，并在持有模块锁之后、紧接发起合并之前进行。发起合并时另外附带 `--no-overwrite-ignore`，作为快进路径上的第二道保险；它不能替代上面的检查。

### 7.5 合并方式

- **纯快进**：本分支是主分支的祖先（本分支没有自己的提交），**并且**主分支提交中任何未归档提案目录下都没有被 git 跟踪的验收与交付标记（§9）。此时快进之后没有任何被跟踪的文件需要改动，结果的 HEAD 就是主分支的提交。
- **不快进的合并**：其余情形，包括「本分支是主分支的祖先，但主分支带有被跟踪的标记」。标记的删除与其他处置一起进入同一个合并提交，提交完成后工作区干净。

这样任何结果为 `synced` 的同步都满足：工作区干净，且结果中报告的提交就是 HEAD。

## 8. 结果与剩余冲突

| 结果 | 含义 | 退出码 |
|---|---|---|
| `synced` | 已把主分支同步进来并完成提交（合并提交或快进） | 0 |
| `up-to-date` | 本分支已包含主分支，未做任何改动 | 0 |
| `conflicts` | 清单内文件与登记表已按规则处理，仍有冲突；合并现场保留 | 2 |

前置条件拒绝与中途失败的退出码为 1。

剩余冲突由三类来源组成，逐个给出路径、类别与原因：

| 原因 `reason` | 来源 |
|---|---|
| `git-conflict` | 处置清单内文件之后，git 索引中仍处于未合并状态的路径 |
| `registry-entry-conflict` | 登记表条目合并出现冲突（§5.5） |
| `baseline-run-diverged` | 基线运行目录中两边改动不同的文件（§4.4） |

类别 `category` 按路径划分：

| 类别 | 路径 |
|---|---|
| `registry` | `logos/logos-project.yaml` |
| `config` | `logos/logos.config.json` |
| `spec` | `logos/resources/` 下除 `verify/` 以外的文件 |
| `verify-record` | `logos/resources/verify/` 下不在清单内的文件 |
| `proposal` | `logos/changes/` 下的文件 |
| `other` | 其余文件（代码等） |

结果为 `conflicts` 时：

- CLI 不修改清单与登记表之外任何文件的冲突内容；
- 合并保持进行中，由调用方解决冲突后自行完成提交，或以 `git merge --abort` 放弃。合并进行期间再次执行 `branch sync` 会以 `BRANCH_OPERATION_IN_PROGRESS` 拒绝；
- 原因为 `registry-entry-conflict` 或 `baseline-run-diverged` 的路径在 git 索引中不一定呈现为未合并。是否还有冲突以本命令的结果为准：调用方在这些路径处理完之前不得完成提交。

## 9. 与验收和交付标记的关系

同步把主分支的新内容带进了本分支，本分支上此前的验收与交付结论不再对应当前内容。

- 只要本次同步引入了主分支的提交（结果为 `synced` 或 `conflicts`），就清除本分支工作区中每个未归档提案目录（`logos/changes/<slug>/`，不含 `archive/`）下的验收与交付标记。清除的集合复用增量修正的失效清单（`AMEND_INVALIDATED_MARKERS`）：`DEPLOY_DONE`、`SMOKE_FAIL`、`SMOKE_PASS`、`VERIFY_FAIL`、`VERIFY_PASS`。
- 被 git 跟踪的标记，其删除计入本次的合并提交；需要删除被跟踪的标记时不走纯快进（§7.5）。未被跟踪的标记直接删除。
- 结果为 `up-to-date` 时不清除任何标记。
- 结果中按提案列出被清除的标记，并提示重新验收。清单内的验收报告与测试结果账本此时是主分支的版本，重新验收会把它们整份重写。

## 10. `branch status`

只读输出：当前分支（分离状态为 `null`）、主分支（引用、来源、提交）、共同起点、本分支落后主分支的提交数与领先的提交数。主分支无法确定时与 `branch sync` 报同样的错误。不检查工作区是否干净，不预测冲突。

## 11. 兼容性

- 不在提案分支上工作、不执行这两个命令的项目，行为不变。
- 既有命令的输出、退出码与写入范围不变；verify 及其沙箱的行为不变。
- `branch_sync` 为可选配置，缺省时主分支取远端默认分支、清单只含内置项。
